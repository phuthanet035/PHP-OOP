1. สถาปัตยกรรมระบบโดยรวม (System Architecture — Diagram 1)

ระบบถูกพัฒนาขึ้นตามแบบสถาปัตยกรรม Custom MVC (Model-View-Controller) บนภาษา PHP 8.2+ โดยไม่พึ่งพา Framework ภายนอก (No Framework) เพื่อให้โครงสร้างโปรแกรมมีขนาดกะทัดรัด ทำงานได้อย่างรวดเร็ว และเป็นไปตามหลักการ Separation of Concerns อย่างเคร่งครัด แบ่งการทำงานออกเป็น 4 เลเยอร์หลัก:

  • Client Layer: สร้าง UI ด้วย HTML5 และ Tailwind CSS ร่วมกับ JavaScript (Fetch API) เพื่อรองรับการอัปเดตข้อมูลแบบเรียลไทม์ (AJAX State Transition)
  • Server Layer: แกนกลางแบบ OOP ประกอบด้วย Router, Middleware Pipeline (Auth / Role / CSRF), Controller Layer, Service Layer (รวม Business Rules), Repository Layer (Data Access), และ Event Dispatcher
  • Data Layer: เชื่อมต่อฐานข้อมูล MySQL 8.0 / MariaDB ผ่าน PHP Data Objects (PDO) แบบ Singleton พร้อมระบบจัดเก็บไฟล์รูปภาพปลอดภัยนอก Document Root (storage/uploads/) และ Audit Trail (status_logs)
  • External Services: เชื่อมต่อ LINE Messaging API ผ่าน Push Message cURL พร้อมระบบ Simulation Logger สำรอง

ฐานข้อมูลประกอบด้วย 6 ตารางหลักที่เชื่อมโยงกันด้วย Foreign Key Constraints เพื่อรักษาความสมบูรณ์ของข้อมูล (Referential Integrity):

ชื่อตาราง คอลัมน์สำคัญ ความสัมพันธ์ (Relations) บทบาทและหน้าที่
users id, name, email, password_hash, role, line_user_id 1 : N กับ tickets, comments, status_logs จัดเก็บข้อมูลผู้ใช้และกำหนดบทบาท (user, technician, admin) พร้อม LINE User ID สำหรับแจ้งเตือน
categories id, name, description 1 : N กับ tickets หมวดหมู่อุปกรณ์ (Hardware, Network, Printer, Software, AV Equipment)
tickets id, user_id, category_id, technician_id, title, description, status, priority, resolved_at, closed_at N : 1 กับ users, categories
1 : N กับ comments, status_logs
1 : 1 กับ ratings		 ตารางหลักจัดเก็บใบแจ้งซ่อม สถานะปัจจุบัน ระดับความเร่งด่วน ช่างผู้รับผิดชอบ และประทับเวลา
comments id, ticket_id, user_id, body, image_path, created_at N : 1 กับ tickets, users การสื่อสารแบบสองทางระหว่างผู้แจ้งซ่อมและช่าง พร้อมรูปภาพแนบประกอบ
status_logs id, ticket_id, changed_by, from_status, to_status, note, created_at N : 1 กับ tickets, users Audit Trail บันทึกประวัติการเปลี่ยนสถานะทุกขั้นตอน ใครเป็นผู้เปลี่ยน จากสถานะใดไปสถานะใด พร้อมบันทึกเหตุผล
ratings id, ticket_id, score (1-5), feedback, created_at 1 : 1 กับ tickets ผลประเมินความพึงพอใจการบริการ (1-5 ดาว) พร้อมข้อเสนอแนะเมื่อผู้แจ้งยืนยันปิดงาน
หลักความปลอดภัยของฐานข้อมูล: ทุกคำสั่ง SQL ใช้ Prepared Statements ร่วมกับ PDO ป้องกัน SQL Injection 100% และรหัสผ่านผู้ใช้เข้ารหัสด้วยฟังก์ชัน password_hash() อัลกอริทึม BCRYPT

3. วงจรสถานะงานซ่อม (Ticket State Machine — Diagram 3)

ระบบใช้กฎการเปลี่ยนสถานะ 5 ขั้นตอน โดยมี TicketStatusService ทำหน้าที่ตรวจสอบเงื่อนไขทางธุรกิจและสิทธิ์ของผู้กระทำอย่างเข้มงวด ควบคุมด้วย PHP 8.1+ Backed Enum:

ผังการเคลื่อนที่ของสถานะ (State Transition Flow): 1-Way Strict Lifecycle with Controlled Revert
1. Open (รับแจ้ง)  →  2. Assigned (มอบหมายช่าง)  →  3. InProgress (กำลังซ่อม)  →  4. Resolved (ซ่อมเสร็จ)  →  5. Closed (ปิดงานสมบูรณ์)
* กรณีผู้แจ้งไม่พึงพอใจผลงาน: Resolved → InProgress (Revert เพื่อส่งช่างเทคนิคแก้ไขต่อ พร้อมระบุเหตุผล)

ตารางกฎการเปลี่ยนสถานะ (Transition Rules Matrix):

การเปลี่ยนสถานะ (From → To) สิทธิ์ผู้ดำเนินการ (Allowed Role) เงื่อนไขและข้อกำหนดบังคับ (Required Action)
Open → Assigned Admin IT เท่านั้น ต้องระบุ technician_id เพื่อมอบหมายงานให้ช่างที่รับผิดชอบ
Assigned → InProgress ช่างเทคนิคที่ได้รับมอบหมาย ช่างกดรับงาน พร้อมบันทึกข้อความเริ่มต้นเข้าตรวจซ่อมอุปกรณ์
InProgress → Resolved ช่างเทคนิคผู้ดูแลงาน บังคับแนบรูปถ่ายผลการซ่อม (Repair Result Photo) และอธิบายวิธีแก้ไขปัญหา
Resolved → Closed ผู้แจ้งซ่อม (Ticket Owner) ประเมินความพึงพอใจ (1-5 ดาว) พร้อมข้อเสนอแนะเพื่อปิดงานอย่างสมบูรณ์
Resolved → InProgress (ส่งแก้) ผู้แจ้งซ่อม (Ticket Owner) ระบุเหตุผลที่งานยังไม่เรียบร้อย เพื่อส่งเรื่องให้ช่างเข้าตรวจสอบแก้ไขซ้ำ

4. การควบคุมสิทธิ์ตามบทบาทผู้ใช้ (Use Case & RBAC — Diagram 4)

👤 ผู้ใช้งานทั่วไป (User)

  • สร้างคำขอแจ้งซ่อม (Create Ticket)
  • แนบรูปถ่ายอาการเสียของอุปกรณ์
  • ติดตามสถานะงานของตนเอง 5 ขั้นตอน
  • สนทนา/ซักถามผ่านระบบคอมเมนต์
  • ตรวจสอบผลงานและประเมิน 1-5 ดาว
  • ส่งแก้ไขงานซ่อมกรณีอุปกรณ์ยังเสีย

🔧 ช่างเทคนิค (Technician)

  • ดูงานทั้งหมด / งานที่ได้รับมอบหมาย
  • กดรับงานซ่อม (Assigned → InProgress)
  • รายงานความคืบหน้าผ่านคอมเมนต์
  • บันทึกซ่อมเสร็จ (InProgress → Resolved)
  • แนบรูปภาพผลการซ่อมตามระเบียบ
  • ดูสถิติและคะแนนดาวผลงานตนเอง

👑 ผู้ดูแลระบบ (Admin IT)

  • มอบหมายงานให้ช่าง (Assign Tech)
  • จัดการผู้ใช้งานในระบบ (เพิ่ม/แก้บทบาท)
  • จัดการหมวดหมู่อุปกรณ์แจ้งซ่อม
  • แดชบอร์ดสถิติ KPI, SLA, Donut Chart
  • ตารางจัดอันดับช่างเทคนิคดีเด่น
  • ตรวจสอบประวัติแจ้งเตือน LINE Logs
Middleware Pipeline: ทุกคำขอที่ส่งเข้ามาจะถูกส่งผ่าน Pipeline: AuthMiddleware → RoleMiddleware → CsrfMiddleware ตรวจสอบ Token อย่างเคร่งครัด ป้องกัน CSRF Attacks และการเข้าถึงข้อมูลโดยไม่ได้รับอนุญาต

5. โครงสร้างคลาสและ Design Patterns (Class Diagram — Diagram 5)

ระบบประยุกต์ใช้ Software Design Patterns ระดับมืออาชีพ เพื่อให้โค้ดสามารถทดสอบได้ง่าย (Testable), บำรุงรักษาง่าย (Maintainable) และขยายขีดความสามารถได้ในอนาคต (Extensible):

Design Pattern คลาสที่นำไปใช้งาน ประโยชน์และความสำคัญเชิงสถาปัตยกรรม
Singleton Pattern App\Core\Database ควบคุมให้มี Connection Pool ของ PDO เพียง Instance เดียวตลอด Request Lifecycle ประหยัดหน่วยความจำและป้องกัน Connection รั่วไหล
Repository Pattern RepositoryInterface
BaseRepository
TicketRepository, UserRepository 		แยกชั้นการเข้าถึงฐานข้อมูล (Data Access) ออกจาก Business Logic ทำให้ Controller ไม่ต้องเขียน Raw SQL โดยตรง และเปลี่ยนฐานข้อมูลได้ง่าย
Service Layer Pattern TicketStatusService
TicketService
DashboardService 		รวบรวม Business Rules ที่ซับซ้อน เช่น การเปลี่ยนสถานะตาม State Machine, การเปิด-ปิด Database Transactions, และการคำนวณสถิติ SLA
Observer Pattern EventDispatcher
TicketObserver 		ลดการผูกมัดของโค้ด (Decoupling) เมื่อมีตั๋วใหม่หรือสถานะเปลี่ยน Service จะ Dispatch Event ออกไปให้ Observer ส่งแจ้งเตือนอัตโนมัติ
Strategy Pattern NotificationChannelInterface
LineMessagingService 		ช่องทางการแจ้งเตือนถูกออกแบบผ่าน Interface ทำให้สามารถเพิ่มช่องทางอื่นในอนาคตได้ เช่น Email, Discord, หรือ SMS โดยไม่ต้องแก้โค้ดเดิม
Backed Enums (PHP 8.1+) TicketStatus, TicketPriority, UserRole Type-Safe Enums ป้องกันข้อผิดพลาดจากการพิมพ์ String ผิดพลาด พร้อมมี Method ในตัว เช่น สี Badge และลำดับ Step ในตัว

10. ขั้นตอนการรันใช้งานระบบ (Deployment Guide)

  1. เริ่มต้นเซิร์ฟเวอร์ MySQL: เปิดโปรแกรม XAMPP Control Panel และกดปุ่ม Start ที่โมดูล MySQL

  5. การรีเซ็ตข้อมูลเริ่มต้น: รันคำสั่ง php init_db.php เพื่อล้างและติดตั้งฐานข้อมูลเริ่มต้นใหม่เมื่อใดก็ได้
